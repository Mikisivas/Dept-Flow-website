# Dept-Flow — database

Postgres schema for Supabase: thirty-four migrations, a development seed, and a
test suite that asserts the rules the rest of the system depends on.

The last nine migrations implement the supervisor's August 2026 revision
(`docs/operational-flow.md`) and reverse three of the original premises. They
are additive files rather than edits to the earlier ones, because a migration
that has been applied to a real project cannot be rewritten — so the history
still contains the GPS columns being created and then dropped, and that is what
it should look like.

## Layout

```
supabase/
  migrations/
    ..._extensions_and_enums.sql       types, and the vocabulary of states
    ..._reference.sql                  academic sessions, venues, config, dues
    ..._identity.sql                   profiles, the register, students, OTP
    ..._academics.sql                  courses, enrolment, timetable, codes
    ..._attendance.sql                 marks, paper batches, session scores
    ..._compliance_and_payments.sql    the state machine, Paystack
    ..._governance.sql                 grace, waivers, disputes, eligibility, audit
    ..._functions.sql                  the attendance formula and transitions
    ..._rls.sql                        row-level security
    ...                                (credentials, grants, venues, course
                                        registration, grace, payment window,
                                        schedules, corrections, permits)

    — the August 2026 revision —
    ..._trust_based_attendance.sql     GPS, geofence and the checkpoint PAIR removed
    ..._registration_gate.sql          semester registration gates attendance
    ..._payment_decoupled.sql          dues stop deciding whether a lecture counts
    ..._channels_and_numbers.sql       WhatsApp number, channels, delivery log
    ..._risk_forecast.sql              the projection, the tiers, the alerts
    ..._reminders_and_reports.sql      pre-lecture reminders, weekly digests
    ..._hod_messaging.sql              three-scope messaging, payment compliance
    ..._permit_dual_condition.sql      dues in full AND 75% per course
    ..._alert_copy_reachability.sql    never promise a threshold that is gone
  seed.sql                             development data, relative to current_date
  seed_today.sql                       a class on today's weekday, for testing
  setup.sql                            GENERATED — every migration, in order
  tests/schema_test.sql                390 assertions
```

`setup.sql` is generated by `npm run build:setup` and is what gets pasted into
the Supabase SQL Editor. Never edit it by hand — it drifted from the migrations
once and the drift was invisible until eight migrations were missing from it.

## Running it

The fast loop, and the one that catches the most:

```bash
./scripts/schema-test.sh
```

It starts a throwaway local Postgres, stubs the Supabase surface a bare
Postgres lacks (`auth.uid()`, the `anon` / `authenticated` / `service_role`
roles, the default grants), regenerates `setup.sql`, applies it, loads the seed
and runs the suite.

It also applies `setup.sql` **inside one explicit transaction**, because the
Supabase SQL Editor runs it that way. That check is not decoration: `ALTER TYPE
… ADD VALUE` cannot be used in the same transaction as a use of the new value,
so an enum extended the obvious way produces a migration that passes every test
outside a transaction and cannot be deployed. Every enum change in the revision
migrations is a full rebuild — rename, create, convert, drop — for that reason.

With the Supabase CLI instead:

```bash
supabase init            # first time only; keeps migrations/ and seed.sql
supabase start
supabase db reset          # applies every migration, then seed.sql
psql "$(supabase status -o env | grep DB_URL | cut -d= -f2-)" \
  -v ON_ERROR_STOP=1 -f supabase/tests/schema_test.sql
```

The test suite runs inside a transaction and rolls back, so it is re-runnable
against a seeded database. Every assertion prints; silence at the end means a
failure aborted the run.

## What the schema is enforcing

Things that are checked here rather than trusted to application code:

- **`(student_id, checkpoint_id)` is unique.** The cheapest defence against
  duplicate submissions, at the only level where it cannot be raced.
- **A score is 1 or 0.** Attendance is present or absent now; there is no
  second checkpoint for a half mark to be half of, and a paper entry cannot
  invent a fraction.
- **Attendance is gated on registration, not on payment.** `attendance_pct()`
  counts every closed lecture the student was enrolled for, whatever they owe.
- **A student who confirms registration late is backfilled absent** for every
  lecture held between the deadline and the moment they confirmed — through
  `resolve_session_score()`, so the rule is not restated in a second place.
- **The exam permit needs both conditions.** `issue_exam_permit()` refuses
  while dues are outstanding, before allocating a reference — a reference is
  permanent, and one allocated for a permit that was never rendered would
  verify against nothing.
- **`CSC` is rejected** as a matric prefix and as a course code.
- **A payment cannot be `success` without a verification timestamp**, so the
  webhook payload alone can never clear a student.
- **A Paystack reference cannot be recorded twice**, which is what stops a
  replayed webhook crediting a student twice.
- **The audit log cannot be updated or deleted from** — by trigger, not
  convention.
- **An authorized eligibility list is frozen.** A correction is a new list.
- **Deactivation, cancellation, grace, waivers, paper batches and HOD messages
  all require a reason**, and `other` requires a note.
- **Only one academic session is active at a time.**

## Row-level security

`authenticated` has SELECT only, scoped by role. Every write of consequence goes
through the API's service role.

The functions matter as much as the tables here. PostgREST publishes everything
in `public` as an RPC and Supabase grants execute to `authenticated` by default,
so a function like `attendance_pct(student, course)` is callable by anybody. It
is safe **only** because it is SECURITY INVOKER: its reads run under the
caller's own RLS and return nothing for a student who is not them. A suite
assertion fails if any function acquires SECURITY DEFINER without needing it.

Two denials worth knowing about, because they are easy to undo by accident:

- **Students cannot read the attendance codes.** The code on the board is the
  entire mechanism now that there is no geo-fence behind it. Handing it to the
  client leaves nothing at all between a student and a mark submitted from the
  car park.
- **Admin cannot read `risk_predictions`.** Individual academic risk is HOD
  scope; surfacing it to the operations role breaks separation of duties, and
  the supervisor's flow states it as a role boundary rather than a screen
  layout.

## What the revision removed

Named because their absence is a decision rather than an omission:

- **No coordinates, anywhere.** No columns, no retention job, no distance, no
  geo-fence, no spoofing detection. `purge_expired_coordinates()` is gone
  because there is nothing left for it to purge.
- **No `score_status`.** Provisional-until-paid was the mechanism payment used
  to gate attendance with, and payment no longer gates attendance.
- **No checkpoint pair.** One code per lecture.

## A note on money

Amounts are kobo in `double precision`, by project decision. Paystack requires
an integer, so the value is cast at the request boundary; reconciliation uses
`payment_matches_dues()` rather than `=`. Instalments mean the fact worth
reading is `dues_balance_kobo()`, not a paid/unpaid flag. See
`docs/decisions.md`.
